# AI Health Assistant — Phase 1 backend

## Implemented contract

`POST /api/assistant/messages` requires an authenticated **Patient** session.
The existing Origin/CSRF, HttpOnly Cookie, role and session checks are reused.
Doctor/Admin roles receive 403; absent/expired sessions receive 401. No route or
permission in another module is changed. There is no migration, chat persistence,
frontend integration, training or fine-tuning.

Request (exact fields only):

```json
{ "message": "What does a balanced meal mean?", "language": "en" }
```

`language` is required (`ar` or `en`). `message` must be a nonblank string, at most
2000 JavaScript string characters before trimming. Unsupported control characters
are rejected. No history, model selection, ownership, medical records or system
instructions are accepted from the request.

Success (200):

```json
{
  "data": {
    "reply": "The actual validated provider response appears here.",
    "language": "en",
    "disclaimer": "This is general health education, not a diagnosis, prescription, or substitute for professional assessment. Do not change treatment based on it.",
    "emergencyGuidance": "For severe or sudden symptoms, or if you believe your life is in danger, contact local emergency services immediately. Do not wait for the assistant."
  }
}
```

Arabic uses fixed Arabic safety text. Only `reply` is generated by the provider.
That example is documentation, not a fallback returned by the application.
Errors retain the existing `{ error: { code, message } }` envelope:

| Status | Code | Meaning |
| --- | --- | --- |
| 400 | INVALID_ASSISTANT_MESSAGE | Invalid/extra fields or message bounds |
| 401 / 403 | Existing auth/role/CSRF codes | Rejected before a provider call |
| 503 | ASSISTANT_NOT_CONFIGURED | Key or model is missing |
| 429 | ASSISTANT_RATE_LIMITED / ASSISTANT_BUSY | Quota or concurrency limit |
| 422 | ASSISTANT_REFUSED | Provider refusal; no invented replacement answer |
| 502 | ASSISTANT_PROVIDER_ERROR / ASSISTANT_INVALID_RESPONSE | Network/provider failure, incomplete or malformed output |
| 504 | ASSISTANT_TIMEOUT | Provider deadline exceeded |
| 499 | ASSISTANT_CANCELLED | Client disconnected/cancelled (response may no longer be deliverable) |

## Configuration

Set values only in backend environment/secrets, never a `VITE_` variable:

| Variable | Required/default | Bounds |
| --- | --- | --- |
| OPENAI_API_KEY | Required to enable assistant | Real project key; never commit or log |
| OPENAI_MODEL | Required to enable assistant | A model available to your project supporting Responses + JSON schema |
| OPENAI_TIMEOUT_MS | 10000 | 1000–12000 ms |
| OPENAI_MAX_OUTPUT_TOKENS | 600 | 128–1000 |

`gpt-4o-mini` is an example in `.env.example`; no live availability/quality check
or automatic model substitution is performed. A missing key/model leaves all
other application features usable and returns 503 for a valid assistant request.
Malformed settings when enabled fail configuration validation with generic errors.
Starting the server never calls the LLM provider.

The adapter calls the official fixed HTTPS `/v1/responses` endpoint via Node fetch
(no SDK dependency), with JSON schema output, `store:false`, one user message and
trusted educational safety instructions. It rejects refusals, incomplete output,
invalid/empty JSON answers and response bodies above 64 KiB. Answer text is capped
at 6000 characters. No tools, files, retrieval, previous_response_id or account
metadata are supplied. The response is plain text: future clients must render it
as text, never unsanitized HTML.

Sources used for the wire format and privacy interpretation:
[Structured Outputs](https://developers.openai.com/api/docs/guides/structured-outputs?api-mode=responses),
[OpenAI data controls](https://developers.openai.com/api/docs/guides/your-data).
`store:false` does not imply Zero Data Retention or absence of provider-side
abuse-monitoring retention. Review the provider's contractual/privacy settings
before deployment.

## Safety, privacy and costs

The prompt restricts replies to general health education and directs individual
diagnosis/treatment questions to qualified clinicians. It prioritizes urgent help
for potential emergencies. Every successful response includes server-controlled
disclaimer and emergency guidance. This is not a validated clinical safety or
triage engine; prompt rules cannot guarantee medically correct model output.
No clinical effectiveness or real-model Arabic/English quality was tested here.

Only the user's submitted message, language instruction, static prompt and fixed
generation/schema settings leave the server. The assistant has no record-store
dependencies, never fetches patient measurements/medications/habits, and does not
write chats to PostgreSQL. Account identity is used locally for authorization and
limits, never sent to OpenAI. Free text can still contain information the patient
chooses to type; it is not automatically anonymized. The future UI must disclose
external processing and advise against including identifying details. Do not log
request/response bodies in proxies, application tracing or APM tooling.

Per server process, the route limits attempts to 20/IP/minute, 5/Patient/minute,
30/Patient/24h, and a conservative shared budget of 200 validated configured
attempts/24h. There is one in-flight call per Patient and at most four total.
Failed/busy requests can consume attempt quotas; these are not billing counters.
Quotas reset on process restart and are not shared between instances. Configure
provider project spending controls and shared gateway limits before scaling.
There are no automatic retries, conversational history growth or background
calls. Client disconnect attempts to cancel the upstream request; cancellation
cannot guarantee that provider processing or billing has already stopped.

## Local verification

Offline/mocked tests (no key, database or paid requests required):

```powershell
Set-Location C:\Users\msi\Desktop\chroniccare-ai\apps\backend
node --import tsx --test tests/assistant.test.ts
npm.cmd run typecheck
npm.cmd run lint
npm.cmd run build
```

For an **explicitly opted-in live test**, configure a server-only key/model and
start the existing backend/frontend normally. After logging in as a Patient, run
this in the browser console on the trusted application origin. This live call
sends the example message externally and can incur provider charges; it was NOT
run automatically during implementation:

```javascript
const api = 'http://localhost:3001/api'; // match the configured host/site exactly
const { csrfToken } = await fetch(`${api}/auth/csrf`, {
  credentials: 'include', cache: 'no-store'
}).then(r => r.json());
const response = await fetch(`${api}/assistant/messages`, {
  method: 'POST', credentials: 'include',
  headers: { 'Content-Type': 'application/json', 'X-CSRF-Token': csrfToken },
  body: JSON.stringify({ message: 'What is general health education?', language: 'en' })
});
console.log(response.status, await response.json());
```

Use an HTTPS API URL in production. Do not use real medical/identifying details
for manual testing. With no key/model configured, the same request must return
503, not an educational example. The frontend Assistant page intentionally remains
unchanged in Phase 1.

## Next phase

Connect the existing frontend to this contract with a clear educational/privacy
notice, visible emergency guidance even when requests fail, pending/error states,
no automatic retries, accessible Arabic/English text rendering and no localStorage
chat persistence. Separately review clinical safety evaluations, provider/privacy
approval, abuse monitoring without sensitive content, and durable cost controls
before claiming production readiness.
