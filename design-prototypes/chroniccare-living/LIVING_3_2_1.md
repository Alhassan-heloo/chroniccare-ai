# Living 3.2.1 — تحقق الأداء

التاريخ: 2026-10-25. النطاق: هذا النموذج المستقل فقط. لا إعادة تصميم ولا حركة جديدة ولا تعديل للبيانات أو الحسابات أو التطبيق الأساسي.

## الخلاصة

لم يمكن إثبات تراجع **3.1 → 3.2**: لا توجد نسخة مصدر قابلة للتشغيل من 3.1. الأرشيفان المرجعيان أقدم منها، وصورها ليست مرجع أداء. ثبتت، بالمقابل، كلفة غير ضرورية لإعادة حساب أنماط Canvas في 3.2 أثناء تحريك المؤشر. عولجت بتغيير هدف متغيرَي الإضاءة فقط.

النتيجة ليست وعدًا بـ60fps على كل جهاز. المقارنة المكتبية تحسنت، لكن بقيت جولة بعد التصحيح ذات P95=33.23ms. تغيّر إيقاع بيئة القياس لاحقًا؛ التفاصيل محفوظة بدل إخفائها.

## البيئة والطريقة

- Windows 10 Pro 19045، Intel Core i7-7700HQ، 4 أنوية/8 خيوط، قرابة 15.92GiB RAM.
- الشاشة النشطة المعلنة 1920×1080 عند 60Hz. Edge أبلغ عن ANGLE/Intel HD Graphics 630 وGPU compositing مفعّل؛ لم يُفترض استخدام GTX 1050.
- Microsoft Edge **156.0.4314.42** المثبّت، Playwright الموجود مسبقًا، **Headless**، DPR=1، دون تثبيت حزم أو CPU/network throttling مقصود. حمل النظام والطاقة والتردد الحراري لم تُعزل مخبريًا.
- بناء Vite Production محلي، على `127.0.0.1:5206`، بلا HMR، مع Cairo المحلي. المعاينة العادية لا تحمل أداة القياس؛ التحميل اختياري بـ`?motion-audit=1` فقط.
- 1440×960 و390×844. السيناريوهات: خمول، تمرير ست مرات PageDown، أربع تبديلات ضغط/سكر مع Living Pulse، دورتا Home/Dashboard، وتفاعلات الماء/الخطوات/التراجع/الجرعات وتقارير 3/7 أيام.
- **100 عينة تطبيق أساسية**: خمسة سيناريوهات × حجمين × Motion On/Off × خمس جولات. العربية/الداكن هما إعداد القياس الأساسي؛ اللغات والمظهران اختُبرا وظيفيًا في مصفوفة منفصلة.
- إعادة تحميل مستند حقيقية لكل عينة، انتظار الخط و1200ms استقرار، نافذة مستهدفة ≥4000ms، وإحماء مستبعد لكل سيناريو/وضع. ترتيب On/Off متناوب بين الجولات الفردية والزوجية.
- على Desktop وصلت 85 pointermove تقريبًا إلى الصفحة في سيناريو Canvas. على الهاتف كانت إحداثيات المسح خارج العرض، وسُجّل pointermove واحد فقط؛ لذلك نتيجته تخص التبويبات ومنزلق الأيام بالمفاتيح، **وليست اختبار لمس أو ضغط مؤشر على الهاتف**. تحقق المؤشر على طبقة الإضاءة نُفذ لاحقًا داخل العرض في الاختبارات الوظيفية.
- rAF هو مقياس تباعد الإطارات، وليس ضمان عرض كل إطار فعليًا على الشاشة. P95 في الجدول هو **وسيط P95 لخمس نوافذ**، لا P95 مجمع لجميع الإطارات. الفاصل الطويل هنا >50ms؛ LoAF وLong Task محفوظان كقياسين منفصلين.
- CPU هو فرق CDP `Performance.getMetrics` حول النافذة نفسها، ويشمل كلفة المقياس/القيادة المشتركة، ولا يقيس GPU. CLS يستخدم نوافذ جلسات 1s/5s ويتجاهل `hadRecentInput`. Event P95 داخل العينة ليس INP ميدانيًا.
- أُخذت 12 Performance Traces منفصلة للتشخيص قبل/بعد (تمرير، Canvas، Dashboard؛ On/Off). لم تدخل كلفتها في العينات الأساسية أو المقارنة المتناوبة. الفئات المتداخلة في التتبّع لا تُجمع كأنها أزمنة CPU مستقلة.

## النتيجة الأساسية قبل التصحيح

الوسيط 16.7ms في جميع مجموعات القياس الأساسية. مع الحركة كان وسيط P95 للتمرير والخمول ولوحة المريض 16.8ms على الحجمين، وللتنقل 17.0ms على Desktop و16.9ms على الهاتف. الاستثناء الواضح: Canvas المكتبي 33.3ms مقابل 16.8ms عند إيقاف الحركة. التفاصيل والعدادات لكل جولة في `artifacts/living-3.2.1/edge/`.

لم تظهر تغييرات DOM مستمرة في عينات الخمول المستقرة. هذا لا يساوي عدّ React commits؛ لم يُستخدم بناء React profiling خاص. التتبّع أظهر كلفة Style/Layout/Paint مرتبطة بالتفاعل، وليس دليلًا على حلقة React لانهائية. لم تثبت مشكلة تستدعي إزالة Pulse أو blur أو SVG أو observers؛ بقيت جميعها.

## الاختناق والتصحيح

كان `useCanvasLight` يكتب `--light-x` و`--light-y` على عنصر `.health-canvas`. هذه متغيرات CSS موروثة، بينما المستهلك الوحيد هو `.canvas-light`؛ الكتابة كانت تُدخل شجرة الرسم والقراءات والجدول في إعادة حساب أنماط غير ضرورية.

في تتبّع Canvas قبل التصحيح: 87 إبطال أنماط بسبب تعديل inline style على حاوية Canvas، وعمليات إعادة حساب وصلت إلى 117–171 عنصرًا. مجموع زيارات العناصر في إعادة حساب الأنماط كان 16,252، وزمن Style قرابة 862.7ms في ذلك التتبّع التشخيصي المفرد. أعطت تجربة عزل غير مشحونة في التطبيق انخفاضًا متكررًا في كلفة Style؛ لم تُعامل هذه التجربة وحدها كإثبات تحسن FPS.

التصحيح في `src/useLivingMotion.ts`: اختيار طبقة الإضاءة، ثم الكتابة والتنظيف عليها بدل الحاوية. بقي حساب الإحداثيات والـRAF والـpointer handlers وحدود القيم والحركة والألوان كما هي. لم يتغير CSS ولا JSX ولا منطق الصحة. بصمة CSS النهائية مطابقة للبناء السابق.

## مقارنة Production قبل/بعد

حُفظ البناء السابق كاملًا داخل `artifacts/living-3.2.1/baseline-dist/`. خدم الخادم البناءين على الأصل نفسه، مع أصول JavaScript مسماة بالبصمة. القياس متناوب baseline/current داخل السياق نفسه، خمس جولات لكل نسخة وحجم، Motion On في النسختين، دون traces متزامنة.

| Desktop بعد | 16.7 | 16.80 | 0 | 1579.601 | 272.208 | 0.003716 |

| 390 بعد، الدفعة نفسها | 33.3 | 33.40 | 0 | 820.141 | 113.794 | 0 |

على Desktop انخفض وسيط Task CPU قرابة **31%** وStyle قرابة **59%** في هذه المقارنة. هذا تحسن محلي مدعوم بقياس؛ ليس إثباتًا لتفوق 3.2.1 على 3.1. نطاق P95 بعد التصحيح 16.8–33.23ms، لذلك لا ادعاء باختفاء كل تفاوت.

**لا تحسن مثبت على الهاتف**. لا يصح مقارنة 33.4ms في إعادة الهاتف بـ16.8ms في الدفعة الأساسية القديمة: تغيّر إيقاع البيئة، وكانت صفحة التحكم الخالية من React تعمل بالإيقاع نفسه قرب 33.3/33.4ms، مع Motion On وOff أيضًا. سبب تغير جدولة البيئة بالضبط لم يُحسم، ولم تُغيّر إعدادات النظام لإجبار نتيجة أفضل. فروق CPU الهاتف الصغيرة والمتفاوتة ليست دليلًا على تحسن أو تراجع عام.

في تتبّع Canvas بعد التصحيح انخفضت كلفة Style التشخيصية إلى نحو 359.0ms، مع بقاء الرسم والإضاءة والتفاعل. هذه عينة تشخيص واحدة، وليست بديلًا عن جدول المقارنة ذي الجولات الخمس.

### مشكلات القياس التي لم تُخفَ

1. المتصفح المضمّن أعطى فواصل مختلفة جدًا عن Edge، ومنها فواصل ~1s مع حجب JavaScript صفري في بعض LoAFs. حُفظت نتائجه منفصلة؛ لم تدخل مقارنة Edge، ولم تُنسب الفواصل وحدها إلى تجمد التطبيق.
2. أصلحت أداة القياس القديمة لتكون جميع العدادات داخل نافذة العينة نفسها، مع percentile صحيح، وتفريغ buffers، وفصل تشخيص عناصر القياس عن التطبيق. ثُبّت حجم لوحة المقياس كي لا تُنشئ CLS ذاتيًا عند تغير نص الزر.
3. انتهى أمر القياس الأساسي بحالة غير صفرية بسبب favicon.ico مفقود **في صفحة التحكم التشخيصية**؛ العينات المئة مكتملة وصالحة المدة (4009.8–4052.9ms). حُدد الرابط في `edge/resource-check.json`، وأضيفت أيقونة SVG الموجودة لصفحة التحكم. إعادة فحص الموارد: لا أخطاء؛ لا تُقدَّم المحاولة الأولى كأمر PASS.
4. احتوت المقارنة الأصلية للهاتف على عينة مدتها 2,403,528.3ms وفاصل يقارب 40 دقيقة، مع زمن Task CPU قرابة 1.1s. السبب الخارجي الدقيق غير محسوم. بقيت العينة الأصلية محفوظة ولم تدخل النتيجة المعتمدة. أعيدت **كل جولات الهاتف الخمس للنسختين** في `edge-comparison-mobile/`؛ مددها 4.23–4.44s. أضيف guard يُوقف الاختبار إذا خرجت النافذة عن 3.9–6s بعد حفظ الأدلة، دون حذف العينة أو اعتبارها نجاحًا.
5. اختبار تغيير media preference احتاج انتظار استجابة حدث `matchMedia` بدل فحص React فورًا؛ صُحح انتظار الاختبار، لا التطبيق.

## التحقق الوظيفي والبصري

- PASS: Home وDashboard في **8 تركيبات**: حجمان × لغتان × مظهران؛ أي 16 حالة صفحة، و16 PNG فعلية كاملة العرض المطلوب دون قص أداة المعاينة.
- PASS: RTL/LTR، عدم overflow أفقي في المستند والحاويات المحددة، Cairo محمّل، سبعة أيام، تبديل اللغة أربع مرات مع حفظ المسار والبيانات، إضافة قياس وتزامن التقرير، الماء/الخطوات والتراجع، تبديل الجرعات وتقارير 3/7 أيام.
- PASS: متغيرات المؤشر على طبقة الإضاءة وحدها، ضمن 0–100%، وتنظيفها عند المغادرة.
- PASS: Motion Off يعطل animation/transition مع بقاء الحفظ والتغذية الراجعة؛ محاكاة `prefers-reduced-motion` مباشرة داخل Edge ذهابًا وإيابًا. هذه محاكاة browser media وليست تغيير إعداد Windows الفعلي.
- أُعيد استخدام `runInteractions` من `living31-browser.mjs` و`storyChecks` من `living32-browser.mjs` عبر موائم صغير لـPlaywright: التركيز أعلى شريط الهاتف، Escape، ربط الخطأ بالحقل، حدود الحقول، القياسات/التقارير، المساعد التجريبي، الإشعارات، كشف القصة مرة واحدة، توقف الخلفية خارج العرض، والحفظ الفعلي لتفضيلات الحركة واللغة والمظهر عبر reload. كلاهما PASS.
- فحص Console في اختبارات التطبيق النهائية: صفر errors/warnings. تحميل Home الوصفي في المصفوفة: CLS بين 0.000022 و0.000975، FCP بين 272 و1180ms، وLCP بين 356 و1232ms. هذه ملاحظات تحميل محلي مفردة لكل حالة، وليست benchmark تحميل بخمس جولات أو نتائج إنترنت ميدانية.

الصور في `artifacts/living-3.2.1/edge-after/`، بأسماء مثل `1440-ar-dark-home.png` و`390-en-light-dashboard.png`. لم تُصنع مقارنة شكلية قبل/بعد: التعديل تنفيذي تحت المظهر، لا إعادة تصميم.

## إعادة التشغيل والقياس على Windows

من مجلد هذا النموذج:

```powershell
npm.cmd run build
node scripts/motion-preview.mjs
```

في نافذة أخرى، مع تعديل مسار Playwright فقط إذا كان تثبيته مختلفًا:

```powershell
$env:PLAYWRIGHT_MODULE_PATH='C:\Users\msi\.cache\codex-runtimes\codex-primary-runtime\dependencies\node\node_modules\playwright'
node scripts/edge-performance.mjs
node scripts/edge-performance.mjs --compare
node scripts/edge-performance.mjs --compare --mobile-repeat
node scripts/edge-performance.mjs --control-check
node scripts/edge-performance.mjs --verify --after
node scripts/edge-performance.mjs --traces --after
node scripts/performance-report.mjs
```

`--compare` يحتاج snapshot السابق المحفوظ، ولا يعيد تكوين 3.1. `--traces` تشخيص منفصل؛ لا تشغله بالتزامن مع benchmark. إعادة القياس بنفس الأسماء تستبدل نواتج تلك الأداة، لذلك انسخ مجلد artifacts إذا أردت حفظ جولة جديدة مستقلة. `--probe-light` يعزل المتغيرات على البناء السابق لأغراض التشخيص فقط. العنوان العادي `http://127.0.0.1:5206/` يعرض Production بلا المقياس. Ctrl+C يوقف خادم المعاينة الذي شغّلته فقط.

Chrome المستقل وFirefox وSafari، هاتف فعلي متوسط/ضعيف، جلسة Edge مرئية Headful طويلة، GPU utilization فعلي، وعداد React commits المباشر لم تُختبر هنا. لا شهادة WCAG شاملة أو ضمان أداء لكل الأجهزة. ينبغي مراجعة التمرير بالعين في Edge المرئي قبل اعتماد الأداء النهائي؛ لا مساواة بين rAF Headless والإطارات المعروضة فعليًا.
